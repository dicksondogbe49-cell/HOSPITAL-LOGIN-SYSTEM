# System Implementation Report: Secure Login and Hospital Workflow Application

## Introduction

This report explains how the Secure Login application has been implemented, from its overall design and startup sequence to its database, authentication process, role-based workflows, security controls, and planned database backup. The report is based on the files present in the project. It distinguishes implemented features from recommended operational work so that the description remains an accurate account of the system.

The application is a compact full-stack web system intended to demonstrate role-based access to a set of hospital-oriented workflows. A user interacts with a browser interface, which sends requests to an Express web server. The server validates the request, checks the signed-in user and their role, reads or writes data in a local SQLite database, and returns a JSON response for the interface to display. Login requires both a password and an emailed one-time verification code. The project provides workspaces for administrators, doctors, nurses, patients, managers, and imputors.

## System architecture and technologies

The implementation uses Node.js and Express 5 for the server-side application. The package configuration specifies Node.js version 22.15 or later and declares dependencies for SQLite access, environment loading, rate limiting, security headers, and email delivery. The application code is concentrated in `server.js`, while the browser interface is separated into `public/index.html`, `public/styles.css`, and `public/app.js`. Static images are served from the `img` directory. This separation keeps page structure and presentation in the frontend while placing authentication, permissions, database access, and business rules on the server.

The frontend is implemented with standard HTML, CSS, and browser JavaScript rather than a client-side framework. On page load, `app.js` asks the server for the current session state. Depending on whether the user is signed out, waiting to verify an email code, or fully authenticated, the script presents the appropriate login, verification, or role-specific workspace. Form submissions are encoded as JSON requests to the API. Successful changes trigger refreshed account lists, records, vitals, or requests so that the browser reflects persisted database data.

The backend uses `better-sqlite3`, which exposes SQLite through a synchronous JavaScript API, and Nodemailer for email. Environment-specific values are loaded by `dotenv`. Helmet applies common HTTP security headers, and `express-rate-limit` limits repeated login attempts. The server serves the browser files directly, so the usual deployment has the page and API on the same origin. In development, `npm start`, `run-app.cmd`, or the VS Code launch configuration starts the server; the configured server reports its local address at `http://localhost:3000` unless a different port is provided through the environment.

## Startup, configuration, and account provisioning

Before opening the database or listening for requests, the server loads values from `.env` and validates essential configuration. `PASSWORD_PEPPER` and `SESSION_SECRET` must each contain at least 32 characters. A bootstrap administrator username and a bootstrap password of at least 12 characters must also be provided. These values are not meant to be committed to source control; `.env.example` supplies names and example placeholders, while `.gitignore` excludes `.env` and the local `data/` directory.

The application creates the `data` directory if it is missing and opens `data/app.db`. During startup it looks for the configured bootstrap administrator by username. If the account does not exist, the server validates its email address and password, hashes the password using the normal password hashing routine, and inserts the administrator. This means the initial administrator is provisioned automatically on first launch. Subsequent launches do not overwrite an existing account's password from the environment.

The email configuration supports Gmail SMTP. `SMTP_USER` identifies the sender and defaults to the bootstrap administrator username when it is not set; `SMTP_APP_PASSWORD` must contain the Gmail app password. The system strips whitespace from the app password before use. Verification emails for doctor, nurse, and patient roles go to `OTP_SHARED_EMAIL` when configured. If it is empty, the server sends these roles' codes to the first administrator account. Other roles receive their codes at their own account email addresses. The shared mailbox therefore needs to be controlled by the system operator because access to it can complete verification for the three shared-mailbox roles.

## Data model and persistence

The system persists operational data in a single SQLite database file, `data/app.db`. At startup, SQLite write-ahead logging (WAL) is enabled, together with foreign-key enforcement. WAL improves the way readers and writers can work with the database, while foreign keys help ensure that rows referring to users point to valid user records. The database is initialized in code, so a separate schema installation step is not required for a new local instance.

The `users` table is the central identity table. It stores an integer identifier, a case-insensitive unique username, a password hash, a per-account salt, a role constrained to the system's six roles, and a creation timestamp. Usernames are treated as email addresses by validation in the application. The role constraint is also reflected in the server's role list, which is used when an administrator creates accounts.

The `sessions` table stores authentication state. Its primary key is a hash of the session token rather than the browser token itself. A session refers to a user and records whether the login is in setup, verification, or complete stage, as well as an expiration time. Additional columns store the verification-code digest, its expiry, the failed-attempt counter, and the time the most recent code was sent. Sessions refer to users with a foreign key and are removed if their user is deleted. The server adds missing one-time-code columns during startup for databases created by an older version. If this migration is needed, it removes existing sessions so stale authentication state is not carried forward.

Three tables represent patient-care information. `medical_records` links a patient and doctor to a diagnosis, optional prescription, notes, and creation timestamp. `vitals` links a patient and nurse to blood pressure, heart rate, temperature, notes, and timestamp. `patient_requests` associates a patient with a support or consultation subject and message. These records are tied to user accounts through foreign keys. The clinical tables and patient requests cascade when the referenced patient is removed; doctor and nurse references on the clinical tables also cascade according to their declared constraints.

The `entries` table supports the general imputor and manager workflow. It stores a title, optional notes, the user who created the entry, and the creation timestamp. Managers can review recent entries with the submitter's username. The schema uses integer primary keys for records and timestamps generated by SQLite's `CURRENT_TIMESTAMP` default for business records. Session expiry and OTP timing use millisecond values generated by the server.

The server contains an additional migration path for earlier versions of the `users` table. If the existing table definition does not include the doctor role, the code temporarily disables foreign-key checking, builds a replacement table with the current role constraint, copies existing user rows, replaces the old table, and reenables foreign keys. This lets an existing local database adopt the expanded role set when the server is upgraded. Database backups should be taken before upgrades that may run migrations, as with any data-bearing schema change.

## Authentication and session lifecycle

The login process begins when the browser sends an email username, password, and selected role to `POST /api/login`. The server accepts login selections for all six system roles (`admin`, `nurse`, `doctor`, `patient`, `manager`, and `imputor`). It looks up the account using the username and role, then checks the submitted password against the stored credential. A role mismatch therefore does not authenticate an account even when the username and password are otherwise valid.

Passwords are not stored in plain text. The server uses Node.js `crypto.scrypt` with a newly generated 16-byte random salt for each password and a server-side pepper appended to the submitted password before derivation. The stored hash is a hexadecimal representation of the derived 64-byte value, and the salt is stored separately in hexadecimal form. Verification derives a new value with the saved salt and uses a timing-safe comparison. Scrypt is deliberately more computationally expensive than a simple fast hash, raising the cost of testing guesses if the user table is exposed. The pepper is held in environment configuration rather than in the database, so losing or changing it affects the ability to verify existing password hashes.

When the password is correct, the server first removes expired sessions, then generates a cryptographically random session token. It stores only an HMAC-SHA-256 digest of that token in the database and returns the original token in the `login_session` cookie. The cookie is HttpOnly, uses SameSite Strict, is scoped to `/`, and lasts eight hours. The Secure attribute is enabled when `NODE_ENV` is `production`, meaning a production deployment must use HTTPS for the cookie to be transmitted correctly.

The initial session stage is `verify`, not `complete`. The server generates a cryptographically random six-digit code, associates an HMAC digest of the code with the session, and sets a five-minute expiry. Because the digest is keyed using `SESSION_SECRET` and bound to the session-token hash, the one-time code is not stored as readable text in SQLite. Nodemailer then sends the code in both plain-text and HTML forms through the configured SMTP provider (Gmail by default, or any custom `SMTP_HOST`). If email sending fails, the server removes the pending session, clears the cookie, and returns a service error rather than leaving an authenticated session in place.

To finish sign-in, the browser submits the entered code to `POST /api/2fa/verify`. The server requires an active session in the verification stage, checks the six-digit format and expiry, and compares the received digest with the stored digest in constant time. Incorrect codes increment the attempt counter; after five incorrect attempts, the digest is invalidated and the user must request another code. A successful check changes the session stage to `complete` and clears the stored code digest and expiry, making the code single use. The resend endpoint only operates during verification and enforces a one-minute delay between sends. The login endpoint also applies a limit of ten attempts per fifteen-minute window.

The session inspection route, `GET /api/session`, enables the interface to restore the appropriate screen after a refresh. Logout deletes the database session and clears the browser cookie. Session validity is checked against the database and expiry on API requests; the cookie alone is not treated as proof of an active login.

## Authorization and application workflows

Authorization is enforced by Express middleware for each protected API route. `requireSession` checks that a database-backed session exists, `requireComplete` additionally blocks users who have not completed email verification, and `allowRoles` restricts the route to the listed roles. This means that hiding a button or workspace in the browser does not grant or deny access by itself: the server checks the authenticated role on every relevant endpoint.

The administrator workspace reports total users, counts of doctors, nurses, and patients, and counts of medical records, vitals, and patient requests. Administrators can view the account directory, create or delete accounts across all six roles, review incoming patient consultation/support requests, and trigger manual, emailed, offline-downloaded, or Cloudflare R2 backups.

Doctors can retrieve the patient list, create consultation records, and view incoming patient consultation/support requests (`GET /api/staff/patient-requests`). When a record is submitted, the server verifies that a patient was selected and that the selected account actually has the patient role. The doctor's identity is taken from the authenticated session rather than from a client-submitted doctor identifier. A doctor sees records they created, while an administrator can query all records. Results are ordered newest first and limited to the most recent 100 records.

Nurses can select registered patients, record blood pressure and optional heart rate, temperature, and notes, view recent vitals logs, and review incoming patient consultation/support requests. As in the doctor workflow, the server verifies that the selected user has the patient role and derives the nurse identity from the session. The vitals view includes the patient and nurse account names and is limited to the latest 100 results.

Patients have endpoints to retrieve their own records, vitals, and consultation or support requests. These queries filter by the authenticated user's ID, so a patient cannot choose another patient identifier in the request to access someone else's data. Patients may submit a request with a subject between 2 and 120 characters and a message between 1 and 2,000 characters. Their dashboard summarizes the number of records, vitals, and requests linked to their own account.

The imputor role can submit an entry with a title between 2 and 120 characters and notes of up to 2,000 characters. The manager role can view the most recent 100 entries, including the submitting user and timestamp. Administrators are also allowed to use the entry-view and entry-create endpoints. These general workflows are separate from the clinical-record and vitals tables.

For responses and errors, the API returns JSON with relevant HTTP status codes, including a `GET /api/health` endpoint for platform health probes. A final API error handler logs unexpected server errors and returns a generic message to the browser, rather than exposing internal error details there. Input values are type-checked and length-checked in route handlers before database writes. Database access uses prepared statements, which separates values from SQL command text and helps prevent SQL injection in the implemented queries.

## Frontend interaction and presentation

The browser script centralizes API communication in a helper that sends JSON and includes same-origin browser credentials by default. It reads the current session before choosing a view. Login form submission transitions to the verification screen when the server reports the pending stage; code verification transitions to the dashboard. For completed sessions, the application fetches the role's dashboard data and builds a role-specific workspace.

The admin, doctor, nurse, patient, manager, and imputor workspaces each contain forms or data tables appropriate to that role. After creating an account, record, vital, request, or entry, the interface resets the relevant form and reloads the corresponding data. The frontend escapes values before inserting account details and database content into generated HTML, reducing the risk that stored text is interpreted as markup. The server remains responsible for authorization and data validation; frontend behavior improves usability but is not relied on for access security.

## Security controls and boundaries

The implementation includes several layers of basic protection. Helmet applies HTTP security headers, Express's `x-powered-by` header is disabled, reverse-proxy trust (`trust proxy`) is enabled in production, JSON request bodies are limited to 16 kilobytes, and requests that modify API data are checked against the request origin when an Origin header is present. The session cookie is inaccessible to ordinary browser JavaScript because it is HttpOnly, and SameSite Strict limits cross-site cookie use. Login rate limiting, OTP expiry and attempt limits, random salts, scrypt password derivation, HMAC-protected session and OTP values, and server-side role checks address common attack paths for a demonstration application.

## Implemented database backup and recovery system

The database resides in `DATA_DIRECTORY` (defaulting to `data/app.db`) with SQLite WAL mode enabled. Because copying only `app.db` during active WAL operation can miss uncheckpointed frames, the server uses `better-sqlite3`'s online backup API (`await db.backup(target)`) to create consistent point-in-time snapshots in `BACKUP_DIRECTORY` (defaulting to `backups/`).

Four backup mechanisms are implemented:
1. **Live Mutation Backups**: After any successful data-modifying API request, the server queues a background snapshot (`app-backup-live-*.db`), prunes older live snapshots beyond `MAX_LOCAL_BACKUPS` (default `10`), encrypts the snapshot using `AES-256-GCM` with a key derived from `SESSION_SECRET` via `HKDF-SHA256`, and emails the `.db.enc` file to `BACKUP_EMAIL`.
2. **Scheduled Automatic Backups**: When `AUTO_BACKUP_INTERVAL_MINUTES` is greater than `0`, a background timer creates periodic snapshots (`app-backup-auto-*.db`), prunes local auto-backups to `MAX_LOCAL_BACKUPS`, and uploads to Cloudflare R2 if R2 credentials are configured.
3. **Offline Encrypted Download**: Administrators can download an `AES-256-GCM` encrypted `.db.enc` snapshot directly to their computer via `POST /api/admin/backup/download` and decrypt it offline with `node decrypt_backup.js <encrypted-file> <output.db>`.
4. **Cloudflare R2 Upload**: Administrators can trigger an immediate upload to Cloudflare R2 (`POST /api/admin/backup/cloud`) using one-time R2 credentials without persisting those credentials on the server.

## Conclusion

The Secure Login application is implemented as a Node.js and Express 5 web service with a plain browser frontend and SQLite persistence. It initializes and migrates its database in code, provisions an initial administrator from environment configuration, authenticates passwords with salted scrypt hashes and a server-side pepper, and completes sign-in with time-limited email verification codes. Server middleware protects API routes according to both session state and role, while automated encrypted backups and container/PaaS configurations (`Dockerfile`, `render.yaml`, `railway.json`) make the system ready to deploy on modern hosting platforms.
